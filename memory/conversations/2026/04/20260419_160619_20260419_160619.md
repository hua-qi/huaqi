### **步骤2：创建第一个示例文件（8分钟）**
创建 `day1_hello_langgraph.py`：

```python
#!/usr/bin/env python3
"""
Day 1: LangGraph 第一个示例
学习目标：了解最基本的 Graph 使用
"""

from langgraph.graph import StateGraph, END
from typing import TypedDict

# 1. 定义状态类型
class MyState(TypedDict):
    message: str
    counter: int

# 2. 创建图构建器
builder = StateGraph(MyState)

# 3. 定义节点函数
def node_a(state: MyState) -> MyState:
    """第一个节点：初始化消息"""
    print("执行节点 A")
    return {"message": "Hello LangGraph!", "counter": state.get("counter", 0) + 1}

def node_b(state: MyState) -> MyState:
    """第二个节点：处理消息"""
    print("执行节点 B")
    message = state["message"]
    counter = state["counter"]
    return {"message": f"{message} (已处理 {counter} 次)", "counter": counter}

# 4. 添加节点到图中
builder.add_node("node_a", node_a)
builder.add_node("node_b", node_b)

# 5. 设置入口点
builder.set_entry_point("node_a")

# 6. 添加边（定义执行流程）
builder.add_edge("node_a", "node_b")
builder.add_edge("node_b", END)

# 7. 编译图
graph = builder.compile()

# 8. 执行图
print("\n=== 开始执行 ===")
initial_state = {"message": "", "counter": 0}
result = graph.invoke(initial_state)

print("\n=== 执行结果 ===")
print(f"最终消息: {result['message']}")
print(f"执行次数: {result['counter']}")

# 9. 可视化图（可选）
try:
    # 需要安装 graphviz
    from langgraph.graph import get_graph
    display = get_graph(graph)
    print("\n图结构已生成（如果安装了graphviz）")
except:
    print("\n（跳过可视化，需要安装graphviz）")
```

# 🌐 React SPA vs 传统HTML文件：全面对比

## 📖 基础概念

### **传统HTML文件（多页面应用 - MPA）**
```html
<!-- 每个页面都是独立的HTML文件 -->
<!-- index.html -->
<!DOCTYPE html>
<html>
<head>
    <title>首页</title>
</head>
<body>
    <h1>欢迎来到首页</h1>
    <a href="about.html">关于我们</a>
</body>
</html>

<!-- about.html -->
<!DOCTYPE html>
<html>
<head>
    <title>关于</title>
</head>
<body>
    <h1>关于我们</h1>
    <a href="index.html">返回首页</a>
</body>
</html>
```

### **React SPA（单页面应用）**
```jsx
// 只有一个HTML文件，内容由JavaScript动态生成
// index.html
<!DOCTYPE html>
<html>
<head>
    <title>我的SPA应用</title>
</head>
<body>
    <div id="root"></div>
    <script src="app.js"></script>
</body>
</html>

// App.jsx
function App() {
  const [currentPage, setCurrentPage] = useState('home');
  
  return (
    <div>
      {currentPage === 'home' && <HomePage />}
      {currentPage === 'about' && <AboutPage />}
      <button onClick={() => setCurrentPage('home')}>首页</button>
      <button onClick={() => setCurrentPage('about')}>关于</button>
    </div>
  );
}
```

---

## 🔄 核心区别对比表

| 特性 | 传统HTML文件 (MPA) | React SPA |
|------|-------------------|-----------|
| **页面数量** | 多个HTML文件 | 单个HTML文件 |
| **页面切换** | 整页刷新 | 局部更新，无刷新 |
| **用户体验** | 有白屏等待 | 流畅，类似原生应用 |
| **开发模式** | 文件系统组织 | 组件化开发 |
| **状态管理** | 无状态，依赖URL参数 | 组件状态，全局状态管理 |
| **SEO友好** | ✅ 天生友好 | ⚠️ 需要额外配置 |
| **首次加载** | ✅ 快（只加载当前页） | ⚠️ 慢（加载整个应用） |
| **后续加载** | ⚠️ 慢（每次全量加载） | ✅ 快（只加载数据） |
| **开发复杂度** | 简单 | 复杂（需要构建工具） |
| **适合场景** | 内容型网站，SEO重要 | Web应用，交互复杂 |

## 🏗️ 架构差异

### **传统HTML文件架构：**
```
服务器端：
├── index.html
├── about.html
├── contact.html
├── products.html
└── assets/
    ├── style.css
    └── script.js

客户端请求：
1. 访问 / → 返回 index.html
2. 点击链接 → 请求 about.html
3. 服务器返回完整的 about.html
4. 浏览器重新渲染整个页面
```

### **React SPA架构：**
```
服务器端：
├── index.html (唯一HTML)
└── static/
    ├── bundle.js (所有JS代码)
    ├── vendor.js (第三方库)
    └── styles.css

客户端请求：
1. 访问 / → 返回 index.html + bundle.js
2. 点击链接 → JavaScript处理路由
3. 只请求数据（API调用）
4. 局部更新DOM，不刷新页面
```

## 💻 技术实现对比

### **1. 路由方式**

#### **传统HTML：**
```html
<!-- 服务器端路由 -->
<a href="/about.html">关于</a>
<!-- 点击后：浏览器 → 服务器 → 返回新HTML -->
```

#### **React SPA：**
```jsx
// 客户端路由
import { BrowserRouter, Route, Link } from 'react-router-dom';

function App() {
  return (
    <BrowserRouter>
      <nav>
        <Link to="/">首页</Link>
        <Link to="/about">关于</Link>
      </nav>
      
      <Route path="/" exact component={Home} />
      <Route path="/about" component={About} />
    </BrowserRouter>
  );
}
// 点击后：JavaScript更新URL和组件，不请求服务器
```

### **2. 数据获取**

#### **传统HTML：**
```html
<!-- 数据在HTML中直接渲染 -->
<div class="product">
  <h2>产品名称</h2>
  <p>价格：$100</p>
</div>
<!-- 更新数据需要重新请求整个页面 -->
```

#### **React SPA：**
```jsx
// 动态获取数据
function ProductList() {
  const [products, setProducts] = useState([]);
  
  useEffect(() => {
    // 只获取数据，不刷新页面
    fetch('/api/products')
      .then(res => res.json())
      .then(data => setProducts(data));
  }, []);
  
  return (
    <div>
      {products.map(product => (
        <Product key={product.id} product={product} />
      ))}
    </div>
  );
}
```

### **3. 状态管理**

#### **传统HTML：**
```javascript

const params = new URLSearchParams(window.location.search);
const userId = params.get('user_id');
```

#### **React SPA：**
```jsx
// 组件状态和全局状态管理
import { useState } from 'react';
import { createStore } from 'redux';

// 组件状态
function Counter() {
  const [count, setCount] = useState(0); // 状态持久在内存中
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

// 全局状态（如Redux）
const store = createStore(reducer);
```

#### **传统HTML（首次访问首页）：**
```
时间线：

0ms: 点击链接

100ms: 接收数据，局部更新DOM
120ms: 页面更新完成
→ 无白屏，只更新必要部分
```

# 🏗️ 微服务架构深度解析

## 📖 基础概念

### **什么是微服务？**
微服务架构是一种将单个应用程序作为**一组小型服务**开发的方法，每个服务运行在自己的进程中，服务之间通过轻量级机制（通常是HTTP RESTful API）进行通信。

### **与单体架构对比：**

#### **单体架构（Monolithic）：**
```
一个大型应用程序，所有功能模块打包在一起
┌─────────────────────────────────┐
│          单体应用                │
│  ┌─────┬─────┬─────┬─────┐      │
│  │用户 │订单 │支付 │库存 │      │
│  │模块 │模块 │模块 │模块 │      │
│  └─────┴─────┴─────┴─────┘      │
│  共享同一个数据库、代码库、部署  │
└─────────────────────────────────┘
```

#### **微服务架构（Microservices）：**
```
多个独立的小服务，每个负责特定业务功能
┌─────┐    ┌─────┐    ┌─────┐    ┌─────┐
│用户服务│    │订单服务│    │支付服务│    │库存服务│
│独立部署│    │独立部署│    │独立部署│    │独立部署│
│独立数据库│   │独立数据库│   │独立数据库│   │独立数据库│
└───┬──┘    └───┬──┘    └───┬──┘    └───┬──┘
    │           │           │           │
    └───────────┼───────────┼───────────┘
                │           │
            ┌───┴───────────┴───┐
            │    API网关/消息总线  │
            └─────────┬─────────┘
                      │
                ┌─────┴─────┐
                │   客户端   │
                └───────────┘
```

---

## 🔄 核心特征对比表

| 特性 | 单体架构 | 微服务架构 |
|------|----------|------------|
| **代码组织** | 单一代码库 | 多个独立代码库 |
| **数据库** | 共享数据库 | 每个服务独立数据库 |
| **部署** | 整体部署 | 独立部署 |
| **技术栈** | 统一技术栈 | 混合技术栈 |
| **扩展性** | 整体扩展 | 按服务扩展 |

# 📡 JSON-RPC 深度解析

## 📖 什么是 JSON-RPC？

### **基本定义：**
JSON-RPC（JavaScript Object Notation Remote Procedure Call）是一种**轻量级的远程过程调用协议**。它使用 JSON（JavaScript Object Notation）作为数据格式，允许客户端调用服务器上的方法（函数）。

### **核心特点：**
- **简单**：基于 JSON，易于理解和实现
- **轻量**：相比 SOAP、XML-RPC 等更轻量
- **语言无关**：任何支持 JSON 的语言都可以使用
- **无状态**：每个请求都是独立的

---

## 🔄 JSON-RPC 的工作原理

### **基本通信流程：**
```
客户端 (Client)                   服务器 (Server)
     │                                │
     │ 1. 创建 JSON-RPC 请求          │
     │    {                            │
     │      "jsonrpc": "2.0",         │
     │      "method": "add",          │
     │      "params": [1, 2],         │
     │      "id": 1                   │
     │    }                            │
     ├───────────────────────────────►│
     │                                │
     │                                │ 2. 执行方法 add(1, 2)
     │                                │
     │                                │ 3. 返回 JSON-RPC 响应
     │    {                            │
     │      "jsonrpc": "2.0",         │
     │      "result": 3,              │
     │      "id": 1                   │
     │    }                            │
     │◄───────────────────────────────┤
     │                                │
```

### **协议版本：**
1. **JSON-RPC 1.0**：最初版本，相对简单
2. **JSON-RPC 2.0**（当前主流）：增加了更多特性，如：
   - 批量调用（batch）
   - 错误对象标准化
   - 通知（notification，无响应）
   - 参数按名称传递

---

## 🎯 JSON-RPC 解决的核心问题

### **问题1：跨语言/跨平台通信**

#### **传统方案的问题：**
```javascript
// 不同语言间的通信困难
// Java 服务端 + JavaScript 客户端
// 需要复杂的序列化/反序列化
// 协议不统一，集成困难
```

#### **JSON-RPC 的解决方案：**
```json
// 统一使用 JSON 格式
{
  "jsonrpc": "2.0",
  "method": "getUser",
  "params": {"id": 123},
  "id": 1
}
// 任何语言都能解析 JSON
// 标准化的通信协议
```

### **问题2：复杂的 RPC 协议**

#### **传统 RPC 协议（如 SOAP）：**
```xml
<!-- SOAP 示例 - 复杂冗长 -->
<soap:Envelope xmlns:soap="http://www.w3.org/2003/05/soap-envelope">
  <soap:Header>
    <m:Transaction xmlns:m="http://example.org/transaction"
                   soap:mustUnderstand="1">
      5
    </m:Transaction>
  </soap:Header>
  <soap:Body>
    <m:GetUser>
      <m:UserId>123</m:UserId>
    </m:GetUser>
  </soap:Body>
</soap:Envelope>
```

#### **JSON-RPC 的简洁性：**
```json
{
  "jsonrpc": "2.0",
  "method": "getUser",
  "params": {"userId": 123},
  "id": 1
}
// 体积小，解析快，人类可读
```

### **问题3：HTTP 通信的语义不明确**

#### **传统 REST API 的问题：**
```javascript
// RESTful API 的歧义性
GET /users/123          // 获取用户
POST /users            // 创建用户
PUT /users/123         // 更新用户
DELETE /users/123      // 删除用户

// 问题：
// 1. 复杂操作难以映射到 HTTP 方法
// 2. 错误处理不统一
// 3. 文档依赖性强
```

#### **JSON-RPC 的明确性：**
```json
// 所有操作都是方法调用
{
  "jsonrpc": "2.0",
  "method": "createUser",
  "params": {"name": "John", "email": "john@example.com"},
  "id": 1
}

{
  "jsonrpc": "2.0", 
  "method": "deleteUser",
  "params": {"userId": 123},
  "id": 2
}
// 方法名明确，参数结构化
```

## 📋 JSON-RPC 2.0 规范详解

### **1. 请求格式**
```json
{
  // 必须字段
  "jsonrpc": "2.0",      // 协议版本
  "method": "方法名",     // 要调用的方法
  
  // 可选字段
  "params": {},          // 参数（对象或数组）
  "id": 123              // 请求ID（null表示通知）
}
```

### **2. 响应格式**
```json
// 成功响应
{
  "jsonrpc": "2.0",
  "result": "返回结果",   // 方法返回值
  "id": 123              // 对应请求的ID
}

// 错误响应
{
  "jsonrpc": "2.0",
  "error": {
    "code": -32601,      // 错误码
    "message": "Method not found",
    "data": "额外错误信息"
  },
  "id": 123
}
```

### **3. 通知（Notification）**
```json
// 客户端发送，不需要响应
{
  "jsonrpc": "2.0",
  "method": "updateStatus",
  "params": {"status": "online"}
  // 没有 id 字段
}
```

### **4. 批量调用（Batch）**
```json
// 一次发送多个请求
[
  {"jsonrpc": "2.0", "method": "sum", "params": [1,2,4], "id": "1"},
  {"jsonrpc": "2.0", "method": "notify_hello", "params": [7]},
  {"jsonrpc": "2.0", "method": "subtract", "params": [42,23], "id": "2"}
]

// 服务器返回批量响应
[
  {"jsonrpc": "2.0", "result": 7, "id": "1"},

class CalculatorService {
  methods = {
    add: (a, b) => a + b,

        jsonrpc: '2.0',

        id: request.id
      };
      
    } catch (error) {

    }
  }

      jsonrpc: '2.0',

## 🆚 JSON-RPC vs 其他技术对比

### **1. JSON-RPC vs REST**

| 维度 | JSON-RPC | REST |
|------|----------|------|
| **协议** | 应用层协议 | 架构风格 |
| **通信方式** | 方法调用 | 资源操作 |
| **端点** | 通常单个端点 | 多个端点 |
| **HTTP方法** | 主要POST | GET/POST/PUT/DELETE等 |
| **数据格式** | JSON | JSON/XML/其他 |
| **错误处理** | 标准化错误对象 | 依赖HTTP状态码 |
| **文档** | 需要方法文档 | 需要端点文档 |
| **适用场景** | 复杂操作，RPC风格 | 资源CRUD，Web服务 |

### **2. JSON-RPC vs GraphQL**

| 维度 | JSON-RPC | GraphQL |
|------|----------|---------|
| **查询语言** | 无，只有方法调用 | 有查询语言 |
| **数据获取** | 固定返回结构 | 客户端指定字段 |
| **类型系统** | 无内置类型系统 | 强类型系统 |
| **复杂度** | 简单 | 相对复杂 |
| **学习曲线** | 低 | 中高 |
| **适用场景** | 简单RPC调用 | 复杂数据查询，前端驱动 |

### **3. JSON-RPC vs gRPC**

| 维度 | JSON-RPC | gRPC |
|------|----------|------|
| **数据格式** | JSON（文本） | Protocol Buffers（二进制） |
| **性能** | 相对较慢 | 高性能 |
| **流支持** | 无 | 支持流式通信 |
| **语言支持** | 任何JSON语言 | 多语言，但需要生成代码 |
| **复杂度** | 简单 | 复杂 |
| **适用场景** | Web前端，简单服务 | 微服务，高性能需求 |

## 📖 基础概念

### **iframe 是什么？**
iframe（内联框架）是 HTML 元素，用于在当前文档中嵌入另一个 HTML 文档。

```html

### **src 属性的作用：**

// 验证 iframe src URL 是否有效的函数
function isValidIframeSrc(url) {
  if (!url || url.trim() === '') {
    return true; // 空字符串加载 about:blank
  }
  
  try {
    const parsed = new URL(url, window.location.href);
    
    // 允许的协议
    const allowedProtocols = [
      'http:',
      'https:',
      'data:',
      'about:',
      'blob:'
    ];
    
    // 检查协议
    if (!allowedProtocols.includes(parsed.protocol)) {
      console.warn(`不支持的协议: ${parsed.protocol}`);
      return false;
    }
    
    // 特殊检查
    if (parsed.protocol === 'data:') {
      // 检查 data URL 格式
      if (!url.startsWith('data:text/html') && 
          !url.startsWith('data:image/svg+xml')) {
        console.warn('data URL 只支持 text/html 或 image/svg+xml');
        return false;
      }
    }
    
    if (parsed.protocol === 'about:') {
      // 只允许特定的 about URL
      const allowedAbout = ['about:blank', 'about:srcdoc'];
      if (!allowedAbout.includes(url.toLowerCase())) {
        console.warn('不支持的 about URL');
        return false;
      }
    }
    
    // 检查域名（可选的安全检查）
    if (parsed.hostname) {
      const blockedDomains = [
        'malicious-site.com',
        'phishing-site.net'
      ];
      
      if (blockedDomains.some(domain => 
        parsed.hostname.includes(domain))) {
        console.warn('域名被阻止');
        return false;
      }
    }
    
    return true;
    
  } catch (error) {
    console.warn('无效的 URL:', error.message);
    return false;
  }
}

# 🚀 OpenRouter 路由配置使用指南

## 📖 什么是 OpenRouter 路由配置？

OpenRouter 的路由配置功能允许你**智能地选择最适合的 AI 模型**来处理不同的请求。你可以根据成本、性能、质量等因素自动路由请求到不同的模型。

## 🔗 访问路由配置页面

### **登录 OpenRouter：**
1. 访问 https://openrouter.ai
2. 点击右上角 "Sign In" 登录
3. 使用 GitHub、Google 或其他方式登录

### **进入路由配置：**
```
登录后 → 点击右上角头像 → Workspaces → Default Workspace → Routing
或直接访问：https://openrouter.ai/workspaces/default/routing
```

# 💻 编码任务的 Token 消耗分析

## 📊 总体趋势

对于大多数编码任务，**Output token 通常比 Input token 高**，但具体比例取决于任务类型。

中等代码生成：Output ≈ 50-100% of Input

### **场景2：函数/方法生成**

```javascript
// Input: 函数签名 + 注释说明
/**
 * 实现快速排序算法
 * @param {number[]} arr - 要排序的数组
 * @returns {number[]} 排序后的数组
 */
function quickSort(arr) {
  // [等待生成实现]
  
// Output: 完整函数实现
  if (arr.length <= 1) return arr;
  
  const pivot = arr[0];
  const left = [];
  const right = [];
  
  for (let i = 1; i < arr.length; i++) {
    if (arr[i] < pivot) {
      left.push(arr[i]);
    } else {
      right.push(arr[i]);
    }
  }
  
  return [...quickSort(left), pivot, ...quickSort(right)];
}
```

#### **Token 比例：**
- **Input**: 低（函数签名和注释）
- **Output**: 高（完整实现）
- **比例**: Output ≈ 200-500% of Input

### **场景3：代码重构/优化**

# Output: 重构后的代码 + 解释
def process_data(data):
    """
    处理数据：偶数乘2，奇数乘3

    return [x * 2 if x % 2 == 0 else x * 3 for x in data]

# 解释：

### **场景4：Bug 修复/调试**

#### **典型模式：**
```javascript
// Input: 有bug的代码 + 错误描述
// 问题：这个函数应该返回数组中的最大值，但有bug
function findMax(arr) {
    let max = 0;
    for (let i = 0; i < arr.length; i++) {
        if (arr[i] > max) {
            max = arr[i];
        }
    }
    return max;
}

// 测试用例：findMax([-5, -3, -1]) 返回 0，应该是 -1

// Output: 修复后的代码 + 解释
function findMax(arr) {
    if (!arr || arr.length === 0) {
        throw new Error('数组不能为空');
    }
    
    let max = arr[0];  // 修复：用第一个元素初始化，而不是0
    for (let i = 1; i < arr.length; i++) {
        if (arr[i] > max) {
            max = arr[i];
        }
    }
    return max;
}

// 解释：
// 1. 修复了初始化问题：max 应该初始化为 arr[0]，而不是 0
// 2. 添加了空数组检查
// 3. 从 i=1 开始循环，避免不必要的比较
```

#### **Token 比例：**
- **Input**: 中等（代码 + 问题描述）
- **Output**: 高（修复代码 + 详细解释）
- **比例**: Output ≈ 200-400% of Input

function estimateCost(inputTokens, outputTokens, model) {
  const rates = {
    'opus': { in: 5, out: 25 },
    'sonnet': { in: 3, out: 15 },
    'haiku': { in: 1, out: 5 },

}
