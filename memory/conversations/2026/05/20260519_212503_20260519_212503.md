## 回合 2

**👤 用户**

tag 和 commit id 绑定吗？

**🤖 Huaqi**

是的，**tag 就是和 commit id 绑定的，而且是一锤子买卖**。

具体来说：

### 怎么绑的

当你打 tag 时，Git 在当前 HEAD 指向的那个 commit 上贴了一个名字。本质上就是：

```
tag "v1.0.0"  →  commit 83a2f1e... 
```

你可以随时查一个 tag 指向哪个 commit：

```bash
git rev-parse v1.0.0       # 输出：83a2f1e...
git show v1.0.0            # 显示那个 commit 的详细信息
```

### 绑定了就不能改

这是 tag 和 branch 最大的区别：

- **branch**：你 `git commit` 之后，branch 自动往前移，指向新的 commit
- **tag**：打上去之后，它就永远钉死在那一个 commit 上，**不会跟着新 commit 走**

如果你想「把 tag 挪到新 commit」，实际上是**删掉旧的，在新区打个同名的**——不是真的移动。

### 重要的实践经验

```bash
# 🌰 场景：你打 tag 后发现漏了一个 commit，想把它包含进来
# 错的：
git tag v1.0.0              # 已经在老 commit 上了

# 对的：
git tag -d v1.0.0           # 删掉旧的
git tag -a v1.0.0 -m "..."  # 在正确的位置重新打
```

### 为什么这个特性重要

正是因为 **tag 绑死了 commit id 且不可变**，你才能放心地用它来做版本发布：

- 别人拉 `v1.0.0`，永远得到同一个代码状态 ✅
- CI/CD 用 tag 触发部署，永远不会因为分支推进而误触发 ✅
- bug 追踪里说「这个 bug 在 v1.0.0 引入的」，排查时能精确定位 ✅

---

所以回答你的问题：**是的，tag 和 commit id 是严格绑定的，绑了就不撒手。** 这也是它和 branch 最本质的区别——branch 是流动的指针，tag 是钉死的锚点。🪨

## 回合 4

**👤 用户**

使用 tag 如何表示首次可用？

**🤖 Huaqi**

好问题。**首次可用**在 Git 的 tag 规范里，业界最通用的做法是：

## ✅ 推荐方案：`v0.1.0`

**遵循语义化版本（SemVer）：** `主版本.次版本.补丁`

- `v0.1.0` — 首个可用版本（可能不完整，但能用）
- `v0.0.1` — 太早期，通常只是原型
- `v1.0.0` — 正式发布，太正式了，不适合「首次可用」

> **惯例**：`v0.1.0` 就是「这个东西跑起来了，你可以试试了」的信号。

## 其他常见做法

| Tag | 含义 | 适合场景 |
|-----|------|----------|
| `v0.1.0` | 首个可用版本 ✅ | **最推荐**，标准 SemVer |
| `v0.0.1` | 非常早期的版本 | 自己测试用的 prototype |
| `v1.0.0-alpha` | 内部可用 | 还没公开但能跑 |
| `v1.0.0-beta` | 外部可试用 | 邀请别人来试 |
| `v1.0.0-rc.1` | 发布候选 | 功能完整，修 bug 阶段 |

## 为什么 `v0.1.0` 比 `v0.0.1` 更好？

因为 `v0.0.x` 约定俗成表示「还不成型的东西」。`v0.1.0` 表示：

- **0** — 还没到 1.0 正式版
- **1** — 但已经有第一个可用的功能集
- **0** — 没修过 bug（刚出来哪来的 bug 😄）

所以你如果是给项目打第一个 tag，通用的做法就是：

```bash
git tag -a v0.1.0 -m "首次可用版本"
git push origin v0.1.0
```

这样别人一看 `v0.1.0` 就知道：**这是这个项目的起点。** 🎯
