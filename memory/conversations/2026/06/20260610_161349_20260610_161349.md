## 问题一：工具链复杂度

**现状**：这个问题目前没有「一键解决」的方案，但生态在收敛。

**已有的缓解手段**：

- **Turborepo**（Vercel 出品）—— 把 monorepo 的 pipeline、缓存、任务编排全封装了，你只需要写一个 `turbo.json`，不用自己搞复杂脚本。是目前最主流的选择。
- **Changesets** —— 专门解决 monorepo 的版本管理和 changelog 生成，比手动管理好太多。
- **统一的脚手架** —— 很多团队会自己做一层 `create-package` CLI，新人跑一条命令就能建好一个标准包，降低入门门槛。

**但说实话**：这个问题的本质是「知识复杂度」，不是工具能完全替代的。无论怎么封装，团队成员还是需要理解 workspace 协议、依赖拓扑、lockfile 这些概念。**工具能降低操作门槛，但不能消除理解门槛。**

---

## 问题二：构建和 CI 复杂度

**这块解决得比较好**，有成熟的方案。

### 增量构建

- **Turborepo**：自动做依赖图分析，只构建受影响的部分，还支持远程缓存（Vercel Remote Caching），CI 里命中缓存直接秒回
- **Nx**（Nrwl 出品）：比 Turborepo 更重但功能更强，支持分布式任务执行（分到多台机器并行跑）
- **pnpm 自身的 `--filter`**：`pnpm --filter=...` 就能精确控制要构建的包

### CI 缓存策略

- 主流 CI（GitHub Actions、GitLab CI）都有 cache action，配合 Turborepo 的远程缓存，基本做到「改一行代码，CI 只跑受影响的两个包」
- **NX Cloud** 和 **Vercel Remote Caching** 都是收费的，但免费额度对小团队够用

### Docker 构建

- 有 **monorepo docker build** 的最佳实践：先复制 lockfile 安装依赖（利用 docker layer 缓存），再复制源码构建——这样只要 lockfile 不变，依赖层就命中缓存

**结论**：这个问题已经有成熟解法了，Turborepo + 远程缓存基本上就是标准答案。

## 问题三：依赖升级的连锁反应

**这个还在解决中，没有完美方案。**

### 现有策略

- **独立版本策略**：不是所有包都用同一个版本。比如 `typescript` 可以做 peer dependency，每个子包声明自己需要的版本范围。但这样又失去了 monorepo 统一管理的优势。
- **依赖升级机器人**：**Renovate** 或 **Dependabot** 配置 monorepo 模式，自动检测子包的依赖更新并提 PR。虽然不能解决冲突，但至少让你「及时知道」。
- **版本对齐检查器**：**syncpack** 这个工具可以强制要求 monorepo 内所有包的某个依赖版本保持一致，如果发现有偏离就报错。相当于在 CI 层加了一道锁。

**但核心矛盾还在**：共享 vs 独立，本身就是 trade-off。你想让所有包用同一个 react 版本享受一致性，就必然被最慢的那个包拖住。唯一的「解决」方式是**合理拆仓**——经常一起变动的放一起，不常变动的或者有特殊版本要求的，考虑拆出去。

## 问题四：Git 仓库体积膨胀

**Git 本身也在进化，这个问题有缓解方案了。**

### Git 层面的解决

- **`git clone --filter=blob:none`**（部分克隆）：只下载你需要的目录及其历史，不下载整个仓库的 blob 对象。GitHub 现在默认就是这种模式了。
- **`git sparse-checkout`**：检出时只拉取指定子目录，比如你只关心 `packages/ui`，那就只拉这个
- **浅克隆 `--depth=1`**：CI 里常用，只要最新版本不要历史

### 仓库管理策略

- **定期 GC**：`git gc` 压缩历史
- **Git LFS**：大文件（二进制、图片）用 LFS 管理，不走 Git 对象存储
- **仓库分拆**：如果某个子包真的巨大且独立（比如设计系统组件库几千个组件），考虑把它拆成独立仓库，用 submodule 或 Git 子仓库引用

**结论**：Git 3 岁以上的 monorepo 确实会有点慢，但配合部分克隆+sparse checkout，日常操作体验已经可以接受了。真正痛的是第一次 clone——几十 G 的仓库，网不好要等很久。

## 问题五：权限管控模糊

**这个是最难解决的，因为它是「组织问题」而非「技术问题」。**

### 现有方案

- **CODEOWNERS**（GitHub/GitLab 原生支持）：每个子目录指定谁有审批权。不解决「能不能看到」，但解决「能不能合入」。
- **Git 子模块**：敏感模块拆成私有子仓库，用 submodule 引用到 monorepo 里。但这样又失去了 monorepo 的一部分优势（跨包重构不方便）。
- **分级仓库策略**（大厂方案）：内层平台层（核心库）是受限访问，上层业务层全可见。两套权限体系用 CI 脚本打通。

### 本质矛盾

Monorepo 的哲学是「透明与共享」，权限管控的哲学是「隔离与限制」。这两个方向是矛盾的。**权限管控在 monorepo 里永远无法做到和 multirepo 一样细粒度**，因为 Git 本身就不支持文件级别的读权限控制。

如果有强制的合规要求（比如金融行业的核心算法只有几个人能看），那 monorepo 可能真的不适合你们。
